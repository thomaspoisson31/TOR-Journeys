VUE D'ENSEMBLE
--------------
Application web de cartographie interactive pour la Terre du Milieu (jeu de rôle).
Architecture modulaire JavaScript avec backend Flask/Python et base SQLite.
Authentification Google OAuth pour sauvegarde cloud synchronisée.

ARCHITECTURE GLOBALE
--------------------

Frontend:
- HTML5 + CSS3 (Tailwind CDN) + Vanilla JavaScript (ES6 modules)
- Architecture modulaire avec pattern Manager
- Responsive design (desktop + mobile)
- Navigation tactile et souris

Backend:
- Flask (Python 3.x)
- Replit Database (Key-Value Store) pour persistance
- Google OAuth 2.0
- API REST pour sync cloud

CONVENTIONS DE CODAGE JAVASCRIPT
---------------------------------

1. STRUCTURE DES MANAGERS:
   - Un fichier = un Manager
   - Export par défaut: export default class NomManager
   - Pattern singleton via window.nomManager
   - Constructor avec injection de dépendances

2. NAMING CONVENTIONS:
   - Classes: PascalCase (DataManager, FilterManager)
   - Fichiers: kebab-case (data-manager.js)
   - Méthodes: camelCase (loadData, applyFilters)
   - Constantes: UPPER_SNAKE_CASE (MAP_WIDTH, MAX_SCALE)
   - Variables globales: camelCase avec window. prefix

3. ORGANISATION DES MÉTHODES:
   class ExampleManager {
       constructor(dependencies, config) { }  // Injection dépendances
       
       init() { }                             // Initialisation
       
       // Méthodes publiques
       publicMethod() { }
       
       // Méthodes privées (préfixe _)
       _privateMethod() { }
       
       // Event handlers
       handleEvent(e) { }
       
       // Getters/Setters
       getData() { }
       setData(data) { }
   }

4. GESTION DES ÉVÉNEMENTS:
   - Listeners dans init() ou setup methods
   - Cleanup explicite si nécessaire
   - Delegation pour éléments dynamiques
   - Arrow functions pour conserver context

5. IMPORTS/EXPORTS:
   // constants.js
   export const CONSTANT_NAME = value;
   
   // manager.js
   import { CONSTANT } from '../utils/constants.js';
   export default class Manager { }

6. LOGGING:
   - Console.log avec emojis pour catégorisation:
     🚀 Initialisation
     ✅ Succès
     ❌ Erreur
     ⚠️  Warning
     📍 Position/Navigation
     🗺️  Carte
     🔍 Zoom/Filtres
     📱 Mobile/Touch
     🗑️  Suppression

7. SUPPRESSIONS EN MASSE:
   - Toujours filtrer par carte active (mapId) avant suppression
   - Double confirmation obligatoire avec messages clairs
   - Afficher le nombre d'éléments à supprimer
   - Préserver les éléments sans mapId (rétrocompatibilité)
   - Préserver les éléments d'autres cartes
   - Marquer comme unsaved après suppression pour sync cloud
   - Notifications utilisateur (succès/erreur/info)
   - Pattern: showNotification(title, message, type)

STRUCTURE DONNÉES
-----------------

localStorage keys (cache frontend uniquement):
- middleEarthLocations: { locations: [...] }
- middleEarthRegions: { regions: [...] }
- middleEarthCharacters: { characters: [...] }
- availableMaps: [{ id, name, url, scale, width, height }]
- activeMapUrl: string
- currentCalendarDate: { day, month, season }
- adventurers_position: { x, y, mapId }
- filtersByMap: { [mapId]: { colors, visited, known, regionsOpacity, showLocations, showRegions } }

Note: version.json n'est PAS stocké dans localStorage, toujours chargé depuis le serveur

Cloud (Replit Database - Key-Value Store):
Structure des clés:
- users: dict {google_id: {google_id, name, email, created_at}}
- travel_contexts: dict {google_id_env_prefix: json_string}
  
Format des données stockées:
{
  "locations": { "locations": [...] },  // Chaque location contient associatedCharacters[]
  "regions": { "regions": [...] },      // Chaque region contient associatedCharacters[]
  "calendar": { "day": int, "month": int, "season": string },
  "settings": { "availableMaps": [...], "activeMapUrl": string },
  "journal": { "voyages": [...] },
  "position": { "x": int, "y": int, "mapId": string },
  "filtersByMap": { [mapId]: {...} },
  "characters": { "characters": [...] },  // Chaque character contient associatedLocations[] et associatedRegions[]
  "_environment": "dev_" | "prod_",
  "_saved_at": ISO_timestamp,
  "_sync_timestamp": milliseconds_epoch
}

Note importante sur les relations:
- Les relations Personnages ↔ Lieux/Régions sont BIDIRECTIONNELLES
- Locations/Regions stockent associatedCharacters (array d'IDs)
- Characters stockent associatedLocations et associatedRegions (arrays d'IDs)
- Ces relations sont synchronisées automatiquement lors des sauvegardes cloud
- Format d'export JSON conserve toutes les relations bidirectionnelles

Format Location:
{
  id: number,
  name: string,
  description: string,
  color: string,
  coordinates: { x: number, y: number },
  images: [{ url, type, isDefault }],
  known: boolean,
  visited: boolean,
  mapId: string | undefined,
  Rumeurs: string[],  // Interface avec fond blanc pour édition, séparateur "---" pour créer plusieurs rumeurs
  Tradition_Ancienne: string,
  evenements_voyage: object[],
  associatedCharacters: [characterId1, characterId2, ...]  // IDs des personnages associés (bidirectionnel)
}

Format Region:
{
  id: number,
  name: string,
  description: string,
  color: string,
  points: [{ x, y }],
  images: [],
  known: boolean,
  visited: boolean,
  mapId: string | undefined,
  type: "region",
  associatedCharacters: [characterId1, characterId2, ...]  // IDs des personnages associés (bidirectionnel)
}

Format Character:
{
  id: number,
  name: string,
  description: string,
  type: "PJ" | "PNJ",
  images: [{ url, type }],
  associatedLocations: [locationId1, locationId2, ...],  // IDs des lieux associés
  associatedRegions: [regionId1, regionId2, ...],        // IDs des régions associées
  mapId: string | undefined                              // Carte d'appartenance (filtrage)
}

GESTION DE LA PERSISTANCE
-------------------------

Principe de double stockage:

1. STOCKAGE LOCAL (localStorage):
   - Cache frontend pour performances
   - Chargement immédiat au démarrage
   - Persistance entre sessions navigateur
   - NON synchronisé entre appareils

2. STOCKAGE CLOUD (Replit Database):
   - Source de vérité centrale
   - Synchronisation multi-appareils
   - Séparation dev/prod par préfixe (dev_, prod_)
   - Détection automatique d'environnement

3. FLUX DE SYNCHRONISATION:
   
   Chargement initial:
   - Démarrage → localStorage vide (structure par défaut)
   - Authentification Google réussie
   - Détection environnement (dev_ ou prod_)
   - Chargement depuis Replit DB
   - Application données → localStorage
   - Rendu interface
   
   Sauvegarde:
   - Modification données (lieu, région, etc.)
   - Sauvegarde immédiate → localStorage
   - Marquage "unsaved" (icône cloud)
   - Délai 2 secondes (debounce)
   - Collecte contexte complet
   - Sauvegarde → Replit DB avec préfixe env
   - Marquage "saved" (icône cloud verte)

4. DÉTECTION ENVIRONNEMENT:
   
   Ordre de priorité:
   a) Variable ENV (Secrets Replit)
      - "production" ou "prod" → prod_
      - "development" ou "dev" → dev_
   
   b) Détection automatique
      - REPLIT_DEPLOYMENT=1 → prod_
      - Hostname contient ".replit.app" ET pas REPLIT_DEV_DOMAIN → prod_
      - Sinon → dev_

5. GESTION DES CONFLITS:
   
   - Timestamp de synchronisation (_sync_timestamp)
   - Détection: cloud_timestamp > client_timestamp
   - Résolution manuelle proposée à l'utilisateur
   - Option force_overwrite disponible

6. STRUCTURE REPLIT DATABASE:
   
   Clés:
   - "users": dict des utilisateurs
   - "travel_contexts": dict des contextes de voyage
   
   Format clé contexte: "{google_id}_{env_prefix}"
   Exemples:
   - "101960341020312309143_dev_"
   - "101960341020312309143_prod_"
   
   Valeur: JSON string complet du contexte

7. MÉTADONNÉES:
   
   Chaque sauvegarde inclut:
   - _environment: préfixe utilisé
   - _saved_at: timestamp ISO format
   - _sync_timestamp: milliseconds epoch pour conflits

PRINCIPES D'AFFICHAGE ET RENDERING
----------------------------------

1. DÉTECTION DES LIEUX ET RÉGIONS À PROXIMITÉ DU TRACÉ:
   
   Contexte:
   - Lors du tracé d'un voyage, l'application doit détecter automatiquement les lieux et régions
     proches ou traversés par le tracé
   - Cette détection est essentielle pour générer les descriptions de voyage via Gemini
   
   Problématique résolue:
   - Les lieux et régions n'étaient plus détectés après le refactoring du PathManager
   - Cause: dataManager.locationsData et dataManager.regionsData n'étaient pas synchronisés
     avec les variables globales window.locationsData et window.regionsData
   
   Solution finale:
   a) Synchronisation avant détection (PathManager.detectDiscoveries):
      - Appel systématique de dataManager.syncFromGlobalData() avant toute détection
      - Garantit que le PathManager travaille avec les données les plus récentes
      - Code: if (this.dataManager && typeof this.dataManager.syncFromGlobalData === 'function') {
                  this.dataManager.syncFromGlobalData();
              }
   
   b) Méthode de synchronisation (DataManager.syncFromGlobalData):
      - Copie window.locationsData vers dataManager.locationsData
      - Copie window.regionsData vers dataManager.regionsData
      - Logs détaillés pour traçabilité: nombre de lieux/régions synchronisés
   
   c) Détection des lieux proches (PathManager.detectNearbyLocations):
      - Seuil de proximité: 80 pixels
      - Filtrage par mapId (seuls les lieux de la carte active)
      - Calcul de distance minimale entre chaque lieu et tous les points du tracé
      - Distinction "traversed" (≤20px) vs "nearby" (≤80px)
      - Logs détaillés: statistiques de détection (ajoutés, ignorés par mapId, trop loin, etc.)
   
   d) Détection des régions traversées (PathManager.detectTraversedRegions):
      - Algorithme "point in polygon" pour chaque point du tracé
      - Filtrage par mapId (seules les régions de la carte active)
      - Stockage des segments (entryIndex, exitIndex) pour chaque région
      - Support du format legacy (region.points) et nouveau format (region.coordinates)
      - Logs détaillés: nombre d'intersections, statistiques de traitement
   
   e) Variables globales pour compatibilité:
      - window.journeyPath synchronisé avec PathManager.path
      - window.journeyDiscoveries synchronisé avec PathManager.discoveries
      - window.regionSegments synchronisé avec PathManager.regionSegments
      - Mise à jour systématique après chaque modification
   
   Code concerné:
   - path-manager.js: detectDiscoveries(), detectNearbyLocations(), detectTraversedRegions()
   - data-manager.js: syncFromGlobalData()
   
   Règle impérative:
   - TOUJOURS synchroniser dataManager depuis window avant détection
   - NE JAMAIS supposer que dataManager.locationsData/regionsData sont à jour
   - TOUJOURS vérifier l'existence des données avant traitement
   - TOUJOURS filtrer par mapId pour respecter la carte active

2. RENDERING ONGLETS RELATIONNELS (PERSONNAGES/LIEUX-RÉGIONS):
   
   Contexte:
   - Les onglets "Personnages" (pour lieux/régions) et "Lieux/Régions" (pour personnages)
     affichent des listes dynamiques basées sur les relations bidirectionnelles
   - Ces onglets doivent toujours afficher les données les plus récentes
   
   Problématique résolue:
   - Après sauvegarde en mode édition, l'onglet relationnel restait vide
   - Cause: le re-render était tenté pendant exitEditMode(), créant un conflit avec updateInfoBoxContent()
   
   Solution finale (v1.3.4):
   a) Re-render au clic sur l'onglet (switchTab):
      - Détection de l'onglet activé (personnages/lieux-regions)
      - Vérification du mode (isEditMode = false)
      - Appel conditionnel aux fonctions de rendering:
        * renderPersonnagesTabRead() pour onglet Personnages
        * renderLieuxRegionsTabRead() pour onglet Lieux/Régions
   
   b) Rechargement des données fraîches:
      - Chaque fonction de rendering recharge l'objet depuis window.locationsData/regionsData
      - Garantit l'affichage des associations les plus récentes
      - Normalisation systématique des IDs en String pour comparaisons
   
   c) Nettoyage après sauvegarde (exitEditMode):
      - Masquage explicite des formulaires d'édition
      - Affichage de la div .text-view
      - Re-render immédiat de l'onglet actif avec timeout minimal (10ms)
      - Pas de re-render multiple ni de conflits
   
   Code concerné:
   - infobox-manager.js: switchTab(), exitEditMode()
   - renderPersonnagesTabRead(), renderLieuxRegionsTabRead()

2. SYNCHRONISATION DES DONNÉES AVANT RENDERING:
   
   Ordre de synchronisation critique:
   a) Modification de l'objet dans le tableau local
   b) Synchronisation avec window.locationsData/window.regionsData
   c) Synchronisation avec dataManager.locationsData/dataManager.regionsData
   d) Sauvegarde localStorage via saveToLocal()
   e) Marquer comme unsaved pour sync cloud
   
   Fichiers concernés: main.js, infobox-manager.js

3. RE-RENDER CONDITIONNEL DES VIGNETTES:
   
   Conditions d'affichage:
   - Vignettes 64x64px: affichées si zoom > 50%
   - Cercles colorés: affichés si zoom < 50%
   - Images principales: toujours disponibles dans InfoBox
   
   Code: main.js (renderLocations)

4. FILTRAGE PAR CARTE ACTIVE:
   
   Principe:
   - Chaque élément (location, region, character) possède un mapId
   - Filtrage systématique par mapId avant affichage ou suppression
   - Préservation des éléments sans mapId (rétrocompatibilité)
   
   Code: filter-manager.js, characters-manager.js

5. GESTION DES ÉVÉNEMENTS DRAG & DROP:
   
   Distinction clic vs drag:
   - Seuil de détection: 3 pixels minimum de déplacement
   - Flag hasDraggedLocation pour éviter l'ouverture de l'InfoBox après drag
   - Curseurs adaptatifs: move (survol), grabbing (drag), pointer (défaut)
   
   Code: main.js (handleLocationDragEnd, event listeners)

SYNCHRONISATION DONNÉES (CRITIQUE)
----------------------------------

Principe de triple synchronisation pour locations/regions:
1. Variable locale (locationsData/regionsData dans main.js)
2. Variable globale (window.locationsData/window.regionsData)
3. DataManager (dataManager.locationsData/dataManager.regionsData)

Règle impérative lors de modifications:
- TOUJOURS synchroniser les 3 références AVANT saveToLocal()
- Ordre: locale → window → dataManager → saveToLocal()

Exemple type (changement couleur, drag, création):
```javascript
// 1. Modifier l'objet dans le tableau local
locationsData.locations[index].property = newValue;

// 2. Synchroniser window
window.locationsData = locationsData;

// 3. Synchroniser dataManager
dataManager.locationsData = locationsData;

// 4. Sauvegarder
dataManager.saveLocationsToLocal();
```

Fichiers concernés: main.js (handleLocationDragEnd, confirmColorChange)

PRINCIPES DE RENDERING DESCRIPTIONS VOYAGE
-------------------------------------------

1. SAUVEGARDE DANS LE JOURNAL:
   
   Problématique:
   - Les descriptions de voyage générées par Gemini doivent être sauvegardées dans le journal
   - Le journal (JournalManager) doit pouvoir afficher ces descriptions même après fermeture de l'app
   - Les descriptions sont liées à un tracé spécifique (pathSignature)
   
   Solution implémentée:
   - Sauvegarde automatique dans localStorage via saveJourneyToJournal() après génération
   - Structure des données: journal[] contient des objets voyage avec pathSignature unique
   - Chaque jour du voyage contient: dayNumber, calendarDate, weatherSymbol, discoveries[], description, eventResult
   - Le journal peut contenir plusieurs voyages (array), triés par date de génération
   
   Règles à respecter:
   - Toujours appeler saveJourneyToJournal() après parseAndDisplayAllJourneyDescriptions()
   - Vérifier l'existence de pathSignature pour éviter les doublons (mise à jour si existe)
   - Synchroniser avec le cloud via markAsUnsaved() et scheduleAutoSync()
   - Rafraîchir JournalManager après sauvegarde: window.journalManager.loadJournal()
   
   Code concerné:
   - voyage-manager.js: saveJourneyToJournal(), parseAndDisplayAllJourneyDescriptions()
   - journal-manager.js: loadJournal(), renderJournal()

2. RENDERING MODAL JOURNAL:
   
   Structure d'affichage:
   - Liste dépliable de voyages (titre, date de génération, nombre de jours)
   - Chaque voyage peut être déplié pour voir les détails jour par jour
   - Pour chaque jour: sous-titre avec jour/date/météo/première découverte, événement (si présent), description
   - Bouton suppression par voyage avec confirmation
   - Message "journal vide" si aucun voyage sauvegardé
   
   Gestion de l'état:
   - Vérification Array.isArray() pour la rétrocompatibilité (anciennes sauvegardes)
   - Filtre des valeurs null/undefined dans localStorage
   - Collapse/expand par voyage avec icône chevron dynamique
   - Export markdown disponible pour sauvegarde externe
   
   Code concerné:
   - journal-manager.js: renderJournal(), toggleJourney(), deleteJourney()

3. WORKFLOW GÉNÉRATION → SAUVEGARDE → AFFICHAGE:
   
   Ordre d'exécution critique:
   a) Génération Gemini via generateJourneyDescription()
   b) Parsing JSON et stockage dans this.journeyDescriptions via parseAndDisplayAllJourneyDescriptions()
   c) Sauvegarde dans localStorage (descriptions + journal complet) via saveJourneyToJournal()
   d) Marquage unsaved pour sync cloud
   e) Rafraîchissement JournalManager pour affichage immédiat
   
   Points de vigilance:
   - Ne pas confondre journeyDescriptions (cache local VoyageManager) et journal (persistance JournalManager)
   - journeyDescriptions est lié à un tracé + carte via pathSignature
   - journal stocke l'historique complet de tous les voyages générés
   - Synchronisation bidirectionnelle: localStorage ↔ cloud

PRINCIPES EVENT DELEGATION POUR ÉLÉMENTS DYNAMIQUES
----------------------------------------------------

1. PROBLÉMATIQUE:
   - Les event listeners attachés via addEventListener sont perdus lorsque innerHTML remplace le DOM
   - Les éléments générés dynamiquement (ex: cartes de jours de voyage) ne répondent pas aux clics
   - Solution naïve: réattacher les listeners après chaque rendu → fragile et inefficace

2. SOLUTION: EVENT DELEGATION
   
   Principe:
   - Attacher UN SEUL listener sur le CONTENEUR PARENT (qui n'est jamais recréé)
   - Utiliser event.target.closest() pour détecter l'élément cliqué
   - Le listener capture les événements de tous les enfants (présents et futurs)
   
   Avantages:
   - Fonctionne même après innerHTML (le parent reste intact)
   - Plus performant (un seul listener au lieu de N)
   - Code plus maintenable et robuste
   - Support automatique des éléments ajoutés dynamiquement

3. IMPLÉMENTATION TYPE:
   
   ```javascript
   // ❌ MAUVAISE APPROCHE (listeners perdus après innerHTML)
   document.querySelectorAll('.day-header').forEach(header => {
       header.addEventListener('click', handleClick);
   });
   voyageDaysContent.innerHTML = newHTML; // Listeners perdus !
   
   // ✅ BONNE APPROCHE (event delegation)
   const container = document.getElementById('voyage-days-content');
   
   // Nettoyer les anciens listeners
   if (container._dayHeaderClickListener) {
       container.removeEventListener('click', container._dayHeaderClickListener);
   }
   
   // Créer et stocker le listener
   const dayHeaderClickListener = (e) => {
       const dayHeader = e.target.closest('.day-header');
       if (!dayHeader) return;
       
       const dayCard = dayHeader.closest('.day-card');
       const dayIndex = parseInt(dayCard.dataset.dayIndex);
       
       // Traitement...
   };
   
   container.addEventListener('click', dayHeaderClickListener);
   container._dayHeaderClickListener = dayHeaderClickListener;
   ```

4. VALIDATION ROBUSTE AVANT ACTIONS:
   
   Avant toute action suite à un clic (déplacer marqueur, changer date):
   - Vérifier l'existence des données (dayData, coordinates)
   - Valider les types (typeof === 'number', !isNaN())
   - Logger les erreurs avec contexte détaillé
   - Afficher des messages utilisateur si échec
   - Ne jamais supposer que les données existent

5. GESTION DU DOM APRÈS MODIFICATIONS:
   
   - Marquer visuellement l'élément actif (classe CSS, ring, highlight)
   - Scroller vers l'élément si nécessaire (scrollIntoView)
   - Mettre à jour les indicateurs globaux (date calendrier, position marqueur)
   - Synchroniser avec localStorage et cloud

6. CAS D'USAGE DANS L'APPLICATION:
   
   Fichiers concernés:
   - voyage-manager.js: renderAllDays() avec event delegation sur .day-header
   - journal-manager.js: openJourneyInVoyageModal() avec event delegation pour voyages archivés
   
   Éléments concernés:
   - Cartes de jours (.day-card, .day-header)
   - Boutons d'événements aléatoires (.day-random-event-btn)
   - Éléments de découverte (.discovery-item)

PROBLÈMES RÉSOLUS
-----------------

1. Clics sur en-têtes de jours non détectés (v1.3.8):
   - Problème: Cliquer sur l'en-tête d'un jour (Jour X, date) ne déplaçait pas le marqueur ni ne changeait la date
   - Cause: Event listeners attachés AVANT innerHTML, puis écrasés lors du rendu
   - Impact: Navigation impossible dans le voyage, utilisateur bloqué
   - Solution: Event delegation sur le conteneur parent + validation robuste des données
   - Bénéfices: Fonctionne après tout rendu, plus performant, code plus maintenable
   - Fichiers concernés: voyage-manager.js (renderAllDays), journal-manager.js (openJourneyInVoyageModal)

2. Descriptions voyage non sauvegardées dans le journal (v1.3.6):
   - Problème: Les descriptions générées n'apparaissaient pas dans la modale Journal
   - Cause: saveJourneyToJournal() appelée deux fois mais la seconde écrasait sans les descriptions
   - Impact: Journal vide malgré génération réussie des descriptions
   - Solution: Appel unique de saveJourneyToJournal() APRÈS parseAndDisplayAllJourneyDescriptions()
   - Ordre correct: génération Gemini → parsing → stockage descriptions → sauvegarde journal → refresh UI
   - Fichier concerné: voyage-manager.js (parseAndDisplayAllJourneyDescriptions)

2. Associations personnages non sauvegardées (v1.3.5):
   - Problème: Impossible d'associer/dissocier des personnages à un lieu/région en mode édition
   - Cause: Les checkboxes générées dans renderPersonnagesTabEdit() n'avaient ni attribut `name` ni `data-character-id`
   - Impact: saveEdit() ne pouvait pas récupérer les IDs des personnages sélectionnés
   - Solution: Ajout de l'attribut `data-character-id="${character.id}"` sur chaque checkbox
   - Méthode de récupération: utilisation de `checkbox.dataset.characterId` au lieu de `checkbox.value`
   - Résultat: Les relations bidirectionnelles location↔character fonctionnent correctement
   - Fichier concerné: infobox-manager.js (ligne ~1920 dans renderPersonnagesTabEdit)

2. Onglet Personnages vide après sauvegarde (v1.3.4):
   - Problème: L'onglet "Personnages" restait vide en mode Lecture après une sauvegarde
   - Cause: renderPersonnagesTabRead() jamais appelée lors de exitEditMode(), DOM conservait la structure du mode édition
   - Solutions tentées (échecs):
     * Forcer renderPersonnagesTabRead() dans updateInfoBoxContent() → appelée trop tôt
     * Appeler dans exitEditMode() directement → timing incorrect
     * Multiples appels avec timeouts → fragile et incohérent
   - Solution finale: Re-render au clic sur l'onglet (switchTab) + nettoyage explicite dans exitEditMode()
   - Bénéfices: Données toujours fraîches, pas de conflits, performance optimale
   - Fichier concerné: infobox-manager.js

2. Conflits entre clic et glisser-déposer (v1.3.1):
   - Problème: Lieux devenaient déplaçables au simple clic pour ouvrir l'infobox
   - Cause: Pas de distinction entre mousedown prolongé (drag) et simple clic
   - Solution: Seuil de 3px + flag hasDraggedLocation pour détecter l'intention de l'utilisateur
   - Événements distincts: mousedown (init), mousemove (détection seuil), mouseup (action finale)
   - Fichier concerné: main.js (handleLocationDragEnd, event listeners)

2. Curseur inapproprié sur les lieux (v1.3.1):
   - Problème: Curseur ne changeait plus au survol après corrections du drag
   - Cause: Gestion du curseur supprimée par erreur lors du fix précédent
   - Solution: Rétablissement des event listeners mouseenter/mouseleave avec curseur `move`
   - Curseur par défaut `pointer` défini dans le style initial
   - Fichier concerné: main.js (renderLocations)

3. Import JSON sur tablette (v1.1.4):
   - Problème: Fichiers .json grisés dans l'interface de sélection mobile
   - Cause: Attribut accept=".json" trop restrictif pour certains navigateurs mobiles
   - Solution: accept=".json,application/json" (extension + type MIME)
   - Fichier concerné: index.html (input#import-file-input)

4. Sauvegarde lieux/régions (v1.1.5):
   - Problème: "0 lieux sauvegardés" malgré modifications (drag, couleur)
   - Cause: dataManager.locationsData non synchronisé avec locationsData locale
   - Solution: Triple sync (locale → window → dataManager) avant saveToLocal()
   - Fichiers: main.js (handleLocationDragEnd, confirmColorChange)

5. Perte de données après republish (v1.1.5):
   - Problème: Données perdues lors du déploiement en production
   - Cause: SQLite non persistant sur Replit Deployments
   - Solution: Migration vers Replit Database avec séparation dev/prod
   - Fichiers: app.py, replit_db_manager.py, auth-manager.js

6. Chargement initial lent (v1.1.5):
   - Problème: Données par défaut chargées avant le cloud
   - Cause: loadInitialLocations chargeait depuis localStorage/URL
   - Solution: Structure vide → attente authentification → chargement cloud
   - Fichiers: data-manager.js, auth-manager.js

7. Object Storage non fonctionnel (v1.1.6):
   - Problème: "Failed to retrieve metadata from Google Compute Engine"
   - Cause: Tentative d'accès aux métadonnées GCE non disponibles sur Replit
   - Solution: Utiliser AnonymousCredentials() pour authentification automatique
   - Fichier concerné: app.py (initialisation storage_client)
