VUE D'ENSEMBLE
--------------
Application web de cartographie interactive pour la Terre du Milieu (jeu de rôle).
Architecture modulaire JavaScript avec backend Flask/Python et base SQLite.
Authentification Google OAuth pour sauvegarde cloud synchronisée.

CONVENTIONS DE CODAGE JAVASCRIPT
---------------------------------

1. STRUCTURE DES MANAGERS:
   - Un fichier = un Manager
   - Export par défaut: export default class NomManager
   - Pattern singleton via window.nomManager
   - Constructor avec injection de dépendances

2. NAMING CONVENTIONS:
   - Classes: PascalCase (DataManager, FilterManager)
   - Fichiers: kebab-case (data-manager.js)
   - Méthodes: camelCase (loadData, applyFilters)
   - Constantes: UPPER_SNAKE_CASE (MAP_WIDTH, MAX_SCALE)
   - Variables globales: camelCase avec window. prefix

3. ORGANISATION DES MÉTHODES:
   class ExampleManager {
       constructor(dependencies, config) { }  // Injection dépendances
       
       init() { }                             // Initialisation
       
       // Méthodes publiques
       publicMethod() { }
       
       // Méthodes privées (préfixe _)
       _privateMethod() { }
       
       // Event handlers
       handleEvent(e) { }
       
       // Getters/Setters
       getData() { }
       setData(data) { }
   }

4. GESTION DES ÉVÉNEMENTS:
   - Listeners dans init() ou setup methods
   - Cleanup explicite si nécessaire
   - Delegation pour éléments dynamiques
   - Arrow functions pour conserver context

5. IMPORTS/EXPORTS:
   // constants.js
   export const CONSTANT_NAME = value;
   
   // manager.js
   import { CONSTANT } from '../utils/constants.js';
   export default class Manager { }

6. LOGGING:
   - Console.log avec emojis pour catégorisation:
     🚀 Initialisation
     ✅ Succès
     ❌ Erreur
     ⚠️  Warning
     📍 Position/Navigation
     🗺️  Carte
     🔍 Zoom/Filtres
     📱 Mobile/Touch
     🗑️  Suppression

7. SUPPRESSIONS EN MASSE:
   - Toujours filtrer par carte active (mapId) avant suppression
   - Double confirmation obligatoire avec messages clairs
   - Afficher le nombre d'éléments à supprimer
   - Préserver les éléments sans mapId (rétrocompatibilité)
   - Préserver les éléments d'autres cartes
   - Marquer comme unsaved après suppression pour sync cloud
   - Notifications utilisateur (succès/erreur/info)
   - Pattern: showNotification(title, message, type)

8. GESTION DES FONCTIONS ASYNCHRONES:
   - TOUJOURS déclarer une méthode avec `async` si elle utilise `await`
   - Pattern standard :
     async methodName() {
         try {
             const data = await fetch(url);
             // traitement
         } catch (error) {
             console.error('❌ Erreur:', error);
             alert('Erreur: ' + error.message);
         }
     }
   - Ne jamais utiliser `await` sans `async` (SyntaxError)
   - Toujours gérer les erreurs avec try/catch dans les fonctions async
   - Préférer async/await à .then() pour la lisibilité

Structure des clés:

- travel_contexts: dict {google_id_env_prefix: json_string}
  
Format des données stockées:
{
  "locations": { "locations": [...] },  // Chaque location contient associatedCharacters[]
  "regions": { "regions": [...] },      // Chaque region contient associatedCharacters[]
  "calendar": { "day": int, "month": int, "season": string },
  "settings": { "availableMaps": [...], "activeMapUrl": string },
  "journal": { "voyages": [...] },
  "position": { "x": int, "y": int, "mapId": string },
  "filtersByMap": { [mapId]: {...} },

  "_saved_at": ISO_timestamp,

Note importante sur les relations:
- Les relations Personnages ↔ Lieux/Régions sont BIDIRECTIONNELLES
- Locations/Regions stockent associatedCharacters (array d'IDs)
- Characters stockent associatedLocations et associatedRegions (arrays d'IDs)
- Ces relations sont synchronisées automatiquement lors des sauvegardes cloud
- Format d'export JSON conserve toutes les relations bidirectionnelles

GESTION DE LA PERSISTANCE
-------------------------

Principe de double stockage:

1. STOCKAGE LOCAL (localStorage):
   - Cache frontend pour performances
   - Chargement immédiat au démarrage
   - Persistance entre sessions navigateur
   - NON synchronisé entre appareils

2. STOCKAGE CLOUD (Replit Database):
   - Source de vérité centrale
   - Synchronisation multi-appareils
   - Séparation dev/prod par préfixe (dev_, prod_)
   - Détection automatique d'environnement

3. FLUX DE SYNCHRONISATION:
   
   Chargement initial:
   - Démarrage → localStorage vide (structure par défaut)
   - Authentification Google réussie
   - Détection environnement (dev_ ou prod_)
   - Chargement depuis Replit DB
   - Application données → localStorage
   - Rendu interface
   
   Sauvegarde:
   - Modification données (lieu, région, etc.)
   - Sauvegarde immédiate → localStorage
   - Marquage "unsaved" (icône cloud)
   - Délai 2 secondes (debounce)
   - Collecte contexte complet
   - Sauvegarde → Replit DB avec préfixe env
   - Marquage "saved" (icône cloud verte)

4. DÉTECTION ENVIRONNEMENT:
   
   Ordre de priorité:
   a) Variable ENV (Secrets Replit)
      - "production" ou "prod" → prod_
      - "development" ou "dev" → dev_
   
   b) Détection automatique
      - REPLIT_DEPLOYMENT=1 → prod_
      - Hostname contient ".replit.app" ET pas REPLIT_DEV_DOMAIN → prod_
      - Sinon → dev_

5. GESTION DES CONFLITS:
   
   - Timestamp de synchronisation (_sync_timestamp)
   - Détection: cloud_timestamp > client_timestamp
   - Résolution manuelle proposée à l'utilisateur
   - Option force_overwrite disponible

6. STRUCTURE REPLIT DATABASE:
   
   Clés:
   - "users": dict des utilisateurs
   - "travel_contexts": dict des contextes de voyage
   
   Format clé contexte: "{google_id}_{env_prefix}"
   Exemples:
   - "101960341020312309143_dev_"
   - "101960341020312309143_prod_"
   
   Valeur: JSON string complet du contexte

7. MÉTADONNÉES:
   
   Chaque sauvegarde inclut:
   - _environment: préfixe utilisé
   - _saved_at: timestamp ISO format
   - _sync_timestamp: milliseconds epoch pour conflits

GESTION DES MAPID ET ATTRIBUTION AUTOMATIQUE
--------------------------------------------

1. PRINCIPE DU MAPID:
   
   Chaque élément (lieu, région, personnage) possède un attribut `mapId`:
   - Identifie la carte d'appartenance de l'élément
   - Permet le filtrage et l'affichage par carte active
   - Format: URL de l'image de la carte (ex: "/uploads/user_id/maps/carte.webp")
   - Éléments sans mapId: affichés sur TOUTES les cartes (rétrocompatibilité)

2. ATTRIBUTION AUTOMATIQUE DU MAPID:
   
   Lors de la sauvegarde cloud (syncUserData):
   a) Détection de la carte active (activeMapUrl)
   b) Parcours de tous les lieux/régions
   c) Attribution du mapId aux éléments qui n'en ont pas:
      - location.mapId = activeMapUrl (si absent)
      - region.mapId = activeMapUrl (si absent)
   d) Synchronisation immédiate:
      - Variables globales (window.locationsData, window.regionsData)
      - DataManager (dataManager.locationsData, dataManager.regionsData)
      - localStorage
   e) Sauvegarde cloud avec les mapId mis à jour
   
   Code concerné: auth-manager.js (syncUserData, ligne ~630-680)

3. FILTRAGE PAR CARTE ACTIVE:
   
   Lors du rendering (renderLocations, renderRegions):
   - Filtrage automatique par mapId === activeMapUrl
   - Éléments sans mapId toujours affichés (rétrocompatibilité)
   - Exemple:
     ```javascript
     const locationsOnActiveMap = locations.filter(loc => 
         !loc.mapId || loc.mapId === activeMapUrl
     );
     ```
   
   Code concerné: main.js (renderLocations, renderRegions)

4. PRÉSERVATION DES DONNÉES MULTI-CARTES:
   
   Lors de l'import/export et des suppressions:
   - TOUJOURS filtrer par carte active avant opération
   - TOUJOURS préserver les éléments d'autres cartes
   - TOUJOURS préserver les éléments sans mapId
   - Pattern de fusion:
     ```javascript
     const autresCartes = elements.filter(e => 
         e.mapId && e.mapId !== activeMapUrl
     );
     const merged = [...autresCartes, ...nouveauxElements];
     ```

IMPORT / EXPORT DE DONNÉES
--------------------------

1. FORMAT D'EXPORT:
   
   Structure JSON unifiée:
   ```json
   {
     "locations": [
       {
         "id": "location_123",
         "name": "Nom du lieu",
         "mapId": "/uploads/user_id/maps/carte.webp",
         "coordinates": {"x": 1000, "y": 500},
         "type": "custom",
         ...autres propriétés
       }
     ]
   }
   ```
   
   Principes d'export:
   - Export UNIQUEMENT des éléments de la carte active
   - Filtrage par mapId avant export
   - Préservation de TOUS les attributs (mapId, associatedCharacters, etc.)
   - Nom de fichier: "{NomCarte}_Lieux_Regions.json"
   
   Code concerné: import-export-manager.js (exportUnifiedData)

2. MODES D'IMPORT:
   
   Mode MERGE (fusion intelligente):
   a) Identification des éléments à conserver:
      - Lieux/régions d'AUTRES cartes → conservés intacts
      - Éléments sans mapId → conservés (rétrocompatibilité)
   
   b) Traitement des éléments importés:
      - Comparaison par ID uniquement (PAS par nom)
      - Si ID existe: mise à jour des données
      - Si ID nouveau: ajout à la liste
   
   c) Fusion finale:
      ```javascript
      const autresCartes = existants.filter(e => 
          e.mapId && e.mapId !== activeMapUrl
      );
      const sansMapId = existants.filter(e => !e.mapId);
      const merged = [...autresCartes, ...sansMapId, ...importés];
      ```
   
   d) Synchronisation triple:
      - window.locationsData/regionsData
      - dataManager.locationsData/regionsData
      - localStorage
   
   e) Sauvegarde cloud automatique
   
   Code concerné: import-export-manager.js (mergeLocations, mergeRegions, processImport)

3. WORKFLOW D'IMPORT COMPLET:
   
   1. Sélection du fichier JSON
   2. Validation et parsing des données
   3. Affichage modale de confirmation avec statistiques:
      - Nombre de lieux/régions existants sur carte active
      - Nombre d'éléments à importer (nouveaux vs mises à jour)
      - Résultat après fusion
   4. Confirmation utilisateur
   5. Fusion intelligente (préservation autres cartes)
   6. Triple synchronisation (window → dataManager → localStorage)
   7. Re-render immédiat des éléments
   8. Sauvegarde cloud automatique
   9. Alert de confirmation à l'utilisateur

4. DÉTECTION DES SUPPRESSIONS:
   
   Avant toute sauvegarde cloud (syncUserData):
   a) Récupération des données actuelles du cloud
   b) Filtrage par carte active (cloud ET local)
   c) Comparaison des IDs:
      - Lieux présents dans cloud mais absents localement = suppressions
   d) Si suppressions détectées:
      - Affichage modale d'alerte détaillée:
        * Nombre de suppressions
        * Liste des noms (max 5 + "... et X autres")
        * Carte concernée
        * Environnement (dev/prod)
      - Demande de confirmation utilisateur
      - Si annulation: arrêt de la synchronisation
   
   Code concerné: auth-manager.js (checkForLocationDeletions, showDeletionWarning)

5. GESTION DES ATTRIBUTS SPÉCIAUX:
   
   Lors de l'import/export, préservation de:
   - mapId: attribution automatique si absent
   - associatedCharacters: relations bidirectionnelles
   - Rumeurs: support format simple (string) et multiple (array)
   - images: conversion automatique des anciens formats
   - Tradition_Ancienne: champ optionnel
   - evenements_voyage: événements liés aux voyages
   
   Conversion automatique:
   - image_url (ancien) → images (nouveau)
   - Rumeur (string) → Rumeurs (array)

6. LOGS DE VALIDATION:
   
   Tous les imports/exports loggent:
   - 📤 Export: nombre d'éléments, carte source
   - 📥 Import: validation, parsing, fusion
   - 🔄 Fusion: compteurs AVANT/APRÈS, préservation autres cartes
   - ✅ Succès: confirmation avec statistiques
   - ❌ Erreur: message détaillé + stack trace
   
   Pattern de validation:
   ```javascript
   console.log(`🔄 [mergeLocations] Carte active: ${activeMapUrl}`);
   console.log(`🔄 [mergeLocations] AVANT: ${existants.length} lieux`);
   console.log(`✅ Conservation: ${autresCartes.length} autres cartes`);
   console.log(`🔄 [mergeLocations] APRÈS: ${merged.length} lieux`);
   console.log(`🔄 Détail: ${autresCartes.length} conservés + ${importés.length} importés = ${merged.length} total`);
   ```

7. SYNCHRONISATION POST-IMPORT:
   
   Ordre critique après import:
   1. Fusion des données (mergeLocations, mergeRegions)
   2. Sauvegarde localStorage
   3. Mise à jour window.locationsData/regionsData
   4. Mise à jour dataManager.locationsData/regionsData
   5. Re-render immédiat (renderLocations, renderRegions)
   6. Marquage unsaved
   7. Sauvegarde cloud automatique (sans rechargement)
   8. Alert de confirmation utilisateur
   
   Pattern de sauvegarde:
   ```javascript
   // 1. Fusion
   this.mergeLocations(importedData.locations);
   
   // 2. localStorage
   localStorage.setItem('middleEarthLocations', JSON.stringify(merged));
   
   // 3. Variables globales
   window.locationsData = merged;
   dataManager.locationsData = merged;
   
   // 4. Render
   window.renderLocations();
   
   // 5. Cloud
   window.authManager.manualSync();
   ```

8. COMPATIBILITÉ FORMATS:
   
   L'import supporte plusieurs formats JSON:
   - Format actuel: { locations: [...], regions: [...] }
   - Ancien format: tableau direct [...]
   - Format legacy: avec propriétés obsolètes (auto-conversion)
   
   Validation robuste:
   - Vérification structure (Array.isArray, propriétés requises)
   - Conversion coordonnées (string → number si nécessaire)
   - Validation minimale (3 points pour régions, x/y valides pour lieux)
   - Messages d'erreur détaillés en cas d'échec

DÉTECTION DES RÉGIONS TRAVERSÉES MULTIPLES FOIS
-----------------------------------------------

1. PROBLÉMATIQUE :
   
   Un voyage peut traverser une même région plusieurs fois :
   - Aller-retour dans la même région
   - Boucle qui repasse par la même région
   - Sortie temporaire puis retour
   
   Exemple : "Au sud de la Comté"
   - Entrée à l'index 0, sortie à l'index 43
   - Re-entrée à l'index 94, sortie à l'index 104

2. ARCHITECTURE DE STOCKAGE :
   
   Structure de données `window.regionSegments` :
   ```javascript
   Map<regionName, Array<{entryIndex, exitIndex, region}>>
   ```
   
   Exemple :
   ```javascript
   window.regionSegments.set("Au sud de la Comté", [
       {entryIndex: 0, exitIndex: 43, region: regionObject},
       {entryIndex: 94, exitIndex: 104, region: regionObject}
   ]);
   ```

3. ALGORITHME DE DÉTECTION (PathManager.detectTraversedRegions) :
   
   ```javascript
   const segments = [];
   let inRegion = false;
   let currentSegmentStart = -1;
   
   for (let i = 0; i < pathToUse.length; i++) {
       const isInside = isPointInPolygon(point, regionCoords);
       
       if (isInside && !inRegion) {
           // ENTRÉE dans la région
           currentSegmentStart = i;
           inRegion = true;
       } else if (!isInside && inRegion) {
           // SORTIE de la région
           segments.push({
               entryIndex: currentSegmentStart,
               exitIndex: i - 1,
               region: region
           });
           inRegion = false;
       }
   }
   
   // Cas spécial : encore dans la région à la fin du tracé
   if (inRegion) {
       segments.push({
           entryIndex: currentSegmentStart,
           exitIndex: pathToUse.length - 1,
           region: region
       });
   }
   ```

4. DENSIFICATION DU TRACÉ :
   
   **CRITIQUE** : Tous les indices (`entryIndex`, `exitIndex`, `discoveryIndex`) 
   doivent référencer le **tracé densifié**, pas les waypoints originaux.
   
   ```javascript
   // PathManager.detectTraversedRegions
   const pathToUse = densePath || this.densifyPath(this.path, 25);
   window.densifiedPath = pathToUse; // Sauvegarder globalement
   
   // VoyageManager.buildAbsoluteTimeline
   const totalPathPoints = window.densifiedPath ? 
       window.densifiedPath.length : journeyPath.length;
   ```
   
   Exemple :
   - 10 waypoints → 105 points densifiés (espacement 25px)
   - `entryIndex=0, exitIndex=43` sur 105 points
   - `ratio = 43/105 = 0.41` → Jour 6 sur 15 jours

5. CALCUL DES JOURS DANS VoyageManager.buildAbsoluteTimeline :
   
   Pour chaque segment de région :
   ```javascript
   const startRatio = segment.entryIndex / totalPathPoints;
   const endRatio = segment.exitIndex / totalPathPoints;
   
   const regionStartDay = Math.max(1, Math.ceil(startRatio × totalJourneyDays));
   const regionEndDay = Math.max(regionStartDay, Math.ceil(endRatio × totalJourneyDays));
   
   absoluteTimeline.push({
       discovery: discovery,
       absoluteStartDay: regionStartDay,
       absoluteEndDay: regionEndDay,
       type: 'region',
       segmentIndex: segmentIndex
   });
   ```

6. AFFICHAGE DANS LA TIMELINE :
   
   - Une région avec 2 segments apparaît dans 2 plages de jours différentes
   - Exemple : "Au sud de la Comté"
     * Segment 1 : Jours 1-6
     * Segment 2 : Jours 13-15
   
   - Le `VoyageManager.buildAbsoluteTimeline` crée une entrée par segment
   - Le rendering affiche la région sur tous les jours concernés

PRINCIPES D'AFFICHAGE ET RENDERING
----------------------------------

0. SYNCHRONISATION FILTERLOCATIONS/RENDERLOCATIONS:
   
   Problématique:
   - Après création d'un nouveau lieu, il doit apparaître immédiatement sans rechargement
   - Le nouveau lieu doit respecter les filtres actifs (connu/inconnu, couleur, etc.)
   - Le FilterManager et le rendering doivent être synchronisés
   
   Architecture critique:
   a) filterManager.filterLocations(array) → calcul logique
      - Fonction PURE qui prend un tableau de lieux en entrée
      - Retourne un nouveau tableau filtré selon les règles actives
      - NE touche PAS au DOM, uniquement du calcul
      - Stocke le résultat dans filterManager.filteredLocations
   
   b) filterManager.applyFilters() → affichage DOM
      - Appelle filterLocations() pour recalculer la liste filtrée
      - Puis appelle updateDisplay() pour masquer/afficher les marqueurs existants
      - Suppose que les marqueurs DOM existent déjà
      - Fonctionne en modifiant display: none/block
   
   c) renderLocations() → création marqueurs DOM
      - Crée les éléments <div> des marqueurs dans le DOM
      - Vérifie si chaque lieu est dans filterManager.filteredLocations
      - Crée UNIQUEMENT les marqueurs des lieux filtrés
      - Applique les styles, événements, vignettes
   
   Ordre d'exécution IMPÉRATIF après création lieu:
   1. Ajouter le nouveau lieu à window.locationsData.locations
   2. Synchroniser: window.locationsData = locationsData
   3. Synchroniser: dataManager.locationsData = locationsData
   4. Sauvegarder: dataManager.saveLocationsToLocal()
   5. **Recalculer filtres: filterManager.filteredLocations = filterManager.filterLocations(window.locationsData.locations)**
   6. **Créer marqueurs: renderLocations()** (utilise filteredLocations pour savoir quoi créer)
   7. Marquer unsaved: window.authManager.markAsUnsaved()
   
   Erreur à éviter:
   ❌ Appeler applyFilters() avant renderLocations()
      → updateDisplay() tente de masquer/afficher des marqueurs qui n'existent pas encore
   
   ✅ Appeler filterLocations() puis renderLocations()
      → renderLocations() sait exactement quels marqueurs créer
   
   Code concerné:
   - main.js: confirmLocationCreation() ligne ~1937-1945
   - filter-manager.js: filterLocations(), applyFilters(), updateDisplay()
   
   Règle impérative:
   - filterLocations() = CALCUL (données → données)
   - renderLocations() = CRÉATION DOM (données → marqueurs)
   - applyFilters() = AFFICHAGE DOM (marqueurs existants → visible/caché)
   - TOUJOURS dans cet ordre: calcul → création → affichage

1. DÉTECTION DES LIEUX ET RÉGIONS À PROXIMITÉ DU TRACÉ:
   
   Contexte:
   - Lors du tracé d'un voyage, l'application doit détecter automatiquement les lieux et régions
     proches ou traversés par le tracé
   - Cette détection est essentielle pour générer les descriptions de voyage via Gemini
   
   Problématique résolue:
   - Les lieux et régions n'étaient plus détectés après le refactoring du PathManager
   - Cause: dataManager.locationsData et dataManager.regionsData n'étaient pas synchronisés
     avec les variables globales window.locationsData et window.regionsData
   
   Solution finale:
   a) Synchronisation avant détection (PathManager.detectDiscoveries):
      - Appel systématique de dataManager.syncFromGlobalData() avant toute détection
      - Garantit que le PathManager travaille avec les données les plus récentes
      - Code: if (this.dataManager && typeof this.dataManager.syncFromGlobalData === 'function') {
                  this.dataManager.syncFromGlobalData();
              }
   
   b) Méthode de synchronisation (DataManager.syncFromGlobalData):
      - Copie window.locationsData vers dataManager.locationsData
      - Copie window.regionsData vers dataManager.regionsData
      - Logs détaillés pour traçabilité: nombre de lieux/régions synchronisés
   
   c) Détection des lieux proches (PathManager.detectNearbyLocations):
      - Seuil de proximité: 80 pixels
      - Filtrage par mapId (seuls les lieux de la carte active)
      - Calcul de distance minimale entre chaque lieu et tous les points du tracé
      - Distinction "traversed" (≤20px) vs "nearby" (≤80px)
      - Logs détaillés: statistiques de détection (ajoutés, ignorés par mapId, trop loin, etc.)
   
   d) Détection des régions traversées (PathManager.detectTraversedRegions):
      - Algorithme "point in polygon" pour chaque point du tracé
      - Filtrage par mapId (seules les régions de la carte active)
      - Stockage des segments (entryIndex, exitIndex) pour chaque région
      - Support du format legacy (region.points) et nouveau format (region.coordinates)
      - Logs détaillés: nombre d'intersections, statistiques de traitement
   
   e) Variables globales pour compatibilité:
      - window.journeyPath synchronisé avec PathManager.path
      - window.journeyDiscoveries synchronisé avec PathManager.discoveries
      - window.regionSegments synchronisé avec PathManager.regionSegments
      - Mise à jour systématique après chaque modification
   
   Code concerné:
   - path-manager.js: detectDiscoveries(), detectNearbyLocations(), detectTraversedRegions()
   - data-manager.js: syncFromGlobalData()
   
   Règle impérative:
   - TOUJOURS synchroniser dataManager depuis window avant détection
   - NE JAMAIS supposer que dataManager.locationsData/regionsData sont à jour
   - TOUJOURS vérifier l'existence des données avant traitement
   - TOUJOURS filtrer par mapId pour respecter la carte active

PRINCIPES SYSTÈME DE VOYAGE WAYPOINTS
--------------------------------------

1. ARCHITECTURE DU SYSTÈME:
   
   Principe:
   - Le tracé de voyage utilise un système de waypoints (points d'étape)
   - Le premier waypoint (waypoint 0) est TOUJOURS la position du marqueur Position.png
   - Le premier clic ajoute simultanément le waypoint 0 (marqueur) ET le waypoint 1 (clic)
   - Les clics suivants ajoutent des waypoints consécutifs
   - Le voyage se termine par double-clic (desktop) ou double-tap (mobile)
   
   Workflow:
   a) Activation du mode voyage (icône "Tracer un voyage")
   b) Premier clic:
      - Waypoint 0 = position du marqueur (window.positionManager.currentPosition)
      - Waypoint 1 = position du clic
      - Tracé de la ligne entre les deux points
   c) Clics suivants:
      - Ajout de waypoints consécutifs (2, 3, 4, ...)
      - Tracé de lignes depuis le dernier waypoint
   d) Finalisation:
      - Double-clic (desktop) ou double-tap (mobile)
      - Blocage de l'ajout de nouveaux waypoints (flag isJourneyFinalized)
      - Détection des lieux/régions traversés
      - Affichage du bouton "Voir le voyage"
   
   Code concerné:
   - path-manager.js: handleViewportMouseDown(), handleViewportTouchEnd(), finalizeJourney()
   - voyage-manager.js: calculateDayCoordinates(), buildAbsoluteTimeline()

2. GESTION DES BOUTONS D'ACTION DANS LA ZONE DATE:
   
   Principe:
   - La zone "Date" (distance-container) affiche des boutons contextuels selon l'état du voyage
   - Ces boutons sont mutuellement exclusifs (un seul visible à la fois)
   - Ils permettent des actions immédiates sans ouvrir de modale supplémentaire
   
   États et boutons:
   a) Voyage en cours de tracé (isJourneyFinalized = false):
      - Bouton "Terminer le voyage" visible (fond rouge)
      - Clic = finalizeJourney() (comme un double-clic)
      - Masque le bouton après finalisation
   
   b) Voyage terminé (isJourneyFinalized = true):
      - Bouton "Voir le voyage" visible (fond vert)
      - Clic = ouverture modale voyage-segments-modal
      - Centrage automatique de la carte sur le tracé
   
   c) Mode dessin désactivé:
      - Les deux boutons sont masqués
      - Seules les informations de distance/jours restent visibles
   
   Méthodes de contrôle:
   - showFinishButton() / hideFinishButton()
   - showViewJourneyButton() / hideViewJourneyButton()
   - Appelées dans finalizeJourney(), toggleDrawingMode(), clearPath()
   
   Code concerné:
   - path-manager.js: setupEventListeners(), finalizeJourney()
   - index.html: boutons finish-journey-btn et view-journey-btn

3. BLOCAGE DES WAYPOINTS APRÈS FINALISATION:
   
   Problématique:
   - Après finalisation d'un voyage, l'utilisateur peut continuer à cliquer sur la carte
   - Sans blocage, de nouveaux waypoints s'ajoutent au voyage terminé
   - Cela corrompt les données du voyage (descriptions, découvertes)
   
   Solution:
   - Flag isJourneyFinalized dans PathManager
   - Vérification au début de handleViewportMouseDown():
     ```javascript
     if (this.isJourneyFinalized) {
         console.log("⚠️ Voyage finalisé - impossible d'ajouter des waypoints");
         return;
     }
     ```
   - Réinitialisation du flag lors de toggleDrawingMode() ou clearPath()
   
   Impact:
   - Garantit l'intégrité des données de voyage
   - Force l'utilisateur à commencer un nouveau voyage pour tracer un autre chemin
   - Évite les incohérences entre tracé et descriptions générées
   
   Code concerné:
   - path-manager.js: finalizeJourney(), handleViewportMouseDown(), toggleDrawingMode()

4. RÈGLES IMPÉRATIVES:
   
   ✅ TOUJOURS:
   - Utiliser window.positionManager.currentPosition comme waypoint 0
   - Vérifier isJourneyFinalized avant d'autoriser l'ajout de waypoints
   - Masquer le bouton "Terminer" et afficher "Voir le voyage" après finalisation
   - Bloquer le mode dessin après finalisation (isJourneyFinalized = true)
   - Calculer les coordonnées de chaque jour basées sur les waypoints
   
   ❌ NE JAMAIS:
   - Permettre l'ajout de waypoints après finalisation du voyage
   - Afficher simultanément les boutons "Terminer" et "Voir le voyage"
   - Finaliser un voyage avec moins de 2 waypoints (0 + 1 minimum)
   - Oublier de réinitialiser isJourneyFinalized lors du clearPath()

PRINCIPES EVENT DELEGATION POUR ÉLÉMENTS DYNAMIQUES
----------------------------------------------------

1. PROBLÉMATIQUE:
   - Les event listeners attachés via addEventListener sont perdus lorsque innerHTML remplace le DOM
   - Les éléments générés dynamiquement (ex: cartes de jours de voyage) ne répondent pas aux clics
   - Solution naïve: réattacher les listeners après chaque rendu → fragile et inefficace

2. SOLUTION: EVENT DELEGATION
   
   Principe:
   - Attacher UN SEUL listener sur le CONTENEUR PARENT (qui n'est jamais recréé)
   - Utiliser event.target.closest() pour détecter l'élément cliqué
   - Le listener capture les événements de tous les enfants (présents et futurs)
   
   Avantages:
   - Fonctionne même après innerHTML (le parent reste intact)
   - Plus performant (un seul listener au lieu de N)
   - Code plus maintenable et robuste
   - Support automatique des éléments ajoutés dynamiquement

3. IMPLÉMENTATION TYPE:
   
   ```javascript
   // ❌ MAUVAISE APPROCHE (listeners perdus après innerHTML)
   document.querySelectorAll('.day-header').forEach(header => {
       header.addEventListener('click', handleClick);
   });
   voyageDaysContent.innerHTML = newHTML; // Listeners perdus !
   
   // ✅ BONNE APPROCHE (event delegation)
   const container = document.getElementById('voyage-days-content');
   
   // Nettoyer les anciens listeners
   if (container._dayHeaderClickListener) {
       container.removeEventListener('click', container._dayHeaderClickListener);
   }
   
   // Créer et stocker le listener
   const dayHeaderClickListener = (e) => {
       const dayHeader = e.target.closest('.day-header');
       if (!dayHeader) return;
       
       const dayCard = dayHeader.closest('.day-card');
       const dayIndex = parseInt(dayCard.dataset.dayIndex);
       
       // Traitement...
   };
   
   container.addEventListener('click', dayHeaderClickListener);
   container._dayHeaderClickListener = dayHeaderClickListener;
   ```

4. VALIDATION ROBUSTE AVANT ACTIONS:
   
   Avant toute action suite à un clic (déplacer marqueur, changer date):
   - Vérifier l'existence des données (dayData, coordinates)
   - Valider les types (typeof === 'number', !isNaN())
   - Logger les erreurs avec contexte détaillé
   - Afficher des messages utilisateur si échec
   - Ne jamais supposer que les données existent

5. GESTION DU DOM APRÈS MODIFICATIONS:
   
   - Marquer visuellement l'élément actif (classe CSS, ring, highlight)
   - Scroller vers l'élément si nécessaire (scrollIntoView)
   - Mettre à jour les indicateurs globaux (date calendrier, position marqueur)
   - Synchroniser avec localStorage et cloud

6. CAS D'USAGE DANS L'APPLICATION:
   
   Fichiers concernés:
   - voyage-manager.js: renderAllDays() avec event delegation sur .day-header
   - journal-manager.js: openJourneyInVoyageModal() avec event delegation pour voyages archivés
   
   Éléments concernés:
   - Cartes de jours (.day-card, .day-header)
   - Boutons d'événements aléatoires (.day-random-event-btn)
   - Éléments de découverte (.discovery-item)
